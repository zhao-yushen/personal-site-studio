# 内容与设计

## 从材料中找到可展示的证据

先查看简历版本、项目说明、README、演示入口和媒体目录。PDF、报告与源码只读取与候选作品有关的部分。目录索引的作用是找材料，无需把全部原始内容加载或公开。

资料较多时，可用下表记录决定。已有事实库或内容数据文件可以承担同一作用，无需另建格式。

| 记录项 | 需要回答的问题 |
| --- | --- |
| 身份与事实 | 当前可信版本是什么，依据在哪？ |
| 作品与贡献 | 解决了什么问题，此人实际完成了哪部分？ |
| 可展示证据 | 有真实界面、图表、报告切片、代码或演示吗？ |
| 状态与边界 | 成品、原型、参与项目、在投研究还是概念探索？ |
| 公开范围 | 哪些字段、图片和切片允许公开？ |
| 主要入口 | 访客在哪里理解它，其他页面怎样链接？ |

选择作品看其代表性、可说明性和证据质量，不能只依据资料体积。团队成果要保留协作语境；示例数据不能包装成客户收益。

图片注明其性质：真实软件截图、合成数据演示、方法示意或场景插画。必要时截取用户允许公开的部分，保留有用的轴、图例和上下文；检查画面中的联系方式、证件、内部标识和未公开结果。记录来源与使用许可。

## 去重与操作精简

以访客任务梳理路径，逐项判断重复内容是必要预告，还是重复的完整叙述。

| 常见情况 | 合并方法 |
| --- | --- |
| 同一批作品连续出现两套完整画廊 | 共享项目选择器，通过概览与拆解模式切换 |
| 首页卡片与案例正文逐字重复 | 卡片保留问题、成果切片和入口，证据留在案例 |
| 导航、浮动面板和卡片提供相同操作 | 保留最容易发现的主要入口，按场景提供必要快捷入口 |
| 控件需要先打开多个面板才能操作 | 合并有共同状态的控件，减少中间确认与面板层级 |
| 搜索、分类和归档各自维护作品资料 | 使用同一内容源，分别派生列表与标签 |
| 多个按钮标签不同但行为相同 | 统一标签和行为；标签不同仅用于真实不同的任务 |

不要仅按文字相似度删除内容。跨页上下文、无障碍标签和必要提示可能需要重复。也不要为了减少页面数，把所有研究、实践和产品压成一条长卡片。

新增模块前给出具体价值，例如“通过对照理解不同产品的分析方法”。若删除某模块不会影响任何访客任务，通常应删去或收进次级入口。

## 审美与技术选择

参考研究以设计决策为终点。用户给出网站、视频或 GitHub 项目时，查看可实际获取的页面、代码或画面，记录构图、动效节奏、导航和内容表达；无法查看的部分明确标为未知。少量适配的案例通常比持续扩大参考库有效。

确定：

- **视觉身份**：与此人的研究、创作或产品工作有关的主题。
- **阅读层次**：主标题、说明、正文和证据各自的密度与对比。
- **媒体主角**：真实作品优先，背景留出呼吸和文字安全区。
- **章节差异**：不同景观、机位、材质或光线承担章节转场，保持统一气质。
- **特色交互**：与内容有关的操作产生可解释反馈。

“电影感”可以来自构图、尺度、空气层次和渐进揭示，不必堆叠粒子与镜头旋转。读者进入长文时，应降低运动密度。首屏的印象与后续阅读要一起成立。

选择技术的依据：

| 视觉或交互目标 | 可选技术 |
| --- | --- |
| 层叠景观、光影与轻视差 | 图片分层、CSS、滚动进度与变换 |
| 局部流动、水波、粒子或向量场 | Canvas 或着色器；只在需要区域渲染 |
| 相机、深度、实体空间交互 | WebGL/Three.js 或项目已有渲染方案 |
| 有明确数值关系的探索 | SVG/Canvas 图表与统一计算模型 |
| 快速找到作品、解释作品差异 | 本地检索、筛选或共享字段的对照视图 |

小游戏应有清楚入口、操作提示、退出和回到内容的路径。是否保存分数、访问相机、联网或记录访客数据取决于当前需求与授权；不要作为默认装饰接入。

确定方向后制作一个有代表性的阅读区域和交互状态，实际查看；发现构图问题时先解决比例、留白、文字对比和媒体质量，再增加特效。
